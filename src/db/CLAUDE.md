# Backends, introspection, and capabilities

Rules for `src/db/`. The project-wide guidance is in the root `CLAUDE.md`.

## Engine flavors

- Postgres-wire engines that aren't PostgreSQL are identified once at connect by `PgFlavor` (`src/db/postgres.rs`), read from the `version()` call that doubles as the liveness check. Keep any flavor branching inside the backend so a new engine is handled in one place; `DbPool::pg_flavor()` exists to report the answer, not for callers to branch on. **Prefer a catalog fact over the flavor whenever one exists** — CockroachDB's reserved catalog schemas are found via `table_type = 'SYSTEM VIEW'`, not via its name, which keeps intact the rule that internal objects are identified by catalog facts, never by name patterns, and needs no engine check at all. Likewise, anything varying by *version* within one engine belongs in a catalog query, which reports what the server has rather than what its version implies. Where no catalog fact exists, the flavor picks which catalog to *ask* rather than deciding the answer itself — Materialize's reserved schemas come from `mz_schemas.id`, a query only Materialize can answer.

## Introspection SQL

- Must not lean on PostgreSQL internals it doesn't need: `NULL::text` rather than `NULL::name` (`name` is a PostgreSQL-internal type), and no explicit `LATERAL` on an `unnest` in `FROM` (Postgres implies it; RisingWave's parser rejects it). Both cost nothing on Postgres and were the difference between a working schema tree and none.
- Must survive a server that lacks a column they select — one absent column fails the whole statement and empties the schema tree. `src/db/postgres.rs` handles this by trying the rich query and falling back to a portable shape that selects the missing pieces as the constants they would decode to; the fallback degrades on *any* missing column rather than on a list of known ones. Equally, don't assume a UNION's two halves are disjoint because they are on PostgreSQL: Materialize reports materialized views in both `information_schema` and `relkind = 'm'`, so each half now takes only what the other did not.

## SQL text and the SQLite driver

- **SQLite text reaches sqlx only through `SqlText`** (`sqlite.rs`), which refuses a NUL anywhere in it. sqlx-sqlite 0.8.6 (and 0.9.0) loops forever at 100% CPU on a statement followed by a NUL: its prepare loop advances by SQLite's tail, which stops on the NUL. No timeout reaches the worker thread. A new SQLite path builds its statement with `SqlText::new(..)?.query()`, not `sqlx::query`. `the_driver_is_handed_text_only_through_sql_text` and `only_known_files_hand_sql_text_to_sqlx` fail otherwise. Names from a crafted file's `sqlite_master` can hold a NUL, so "hubro built this text itself" is no exemption.

## Retrying

- A failure the *server* declared retryable is `DbError::Transient`, classified on SQLSTATE `40001` alone and never on message text — YugabyteDB's stale catalog snapshot and CockroachDB's transaction conflicts share the code and share nothing in their wording. Only the multi-statement catalog reads act on it: `DbPool::introspect` and `fetch_ddl` run **once** more via `retry_transient`, because a schema change landing between their queries is nobody's mistake and nothing the user can act on. Never retry a write on it, and never loop — a second failure isn't a racing schema change, and a schema tree that hangs is worse than one that reports an error.

## Credentials

- **`DbError::CredentialsRejected` is the one connect error that may cost a stored secret**: the connect flow reads it as "the remembered password may have gone stale", drops it from session memory and prompts (`password_retry` in `src/ui/state/connect.rs`); the keyring copy is replaced or, unticked, deleted only once a *different* password connects (`stored_password_after_connect`). So it is built from the server's wrong-credentials code and nothing else — SQL Server 18456, PostgreSQL SQLSTATE `28P01` — in one `connect_error_from` per backend, and every other refusal at login stays `DbError::Connect`. The code is the server's word, not proof: measured, a contained-database user naming a missing database, a login denied `CONNECT SQL` and an expired `VALID UNTIL` role all get it with the right password. That is why a refusal alone deletes nothing: those cases cost a needless prompt, and the stored password survives it. Text is not a signal: SQL Server's 4060 ("Cannot open database … The login failed.") is sent for a database that is missing, offline, restoring or forbidden to the login, always *after* the password was accepted, and matching "login failed" on it deleted working passwords. A disabled login (18470) keeps its password too. The SQL Server half also depends on tiberius reporting the *first* of the two ERROR tokens a 4060 login draws (see `LOGIN_FAILED`). A new backend — or a Postgres-wire engine whose wrong-password SQLSTATE is not `28P01` — that never builds the variant never raises the password prompt; one that builds it from text reopens that bug. CockroachDB in secure mode was measured sending `28P01`.

- **An Entra connection's pool renews its login token silently, and stores nothing.** The access token lasts about an hour, and a pool logs in long after: every script run's connection (closed when the run ends) and the driver's replacements for connections it retires. So the pool asks `entra::EntraTokens::current` for the token each new connection logs in with — SQL Server per connection (`PoolInner::login_config`), Postgres by keeping the pool's password current (`postgres::renew_login`, every minute and before each script run takes its connection). Whether to renew is `entra::token_step`, over plain data: within `RENEW_MARGIN` of expiry, if `may_renew` (a managed identity, or a kept refresh token), and not within `RETRY_AFTER` of a failure; an expired token that cannot be renewed fails the login with "reconnect to sign in again". One renewal at a time, shared by the connections waiting for it. The clock is read again after a renewal returns — stamped with its start, a renewal that hung for its HTTP timeout recorded a failure already past `RETRY_AFTER`, and every caller queued behind it renewed again in series — and a renewed token still inside the margin (a managed identity's cached one) counts as a failure for the backoff. Token values are `entra::Secret` from the moment the token endpoint's answer is parsed (`azure::AccessToken`), whose `Debug` and `Display` print `<redacted>`; the value is read only through `expose()`, and only at the sites `EXPOSE_SITES` (in `entra.rs`'s tests) registers with a count and a reason — a driver's login, the token endpoint's refresh grant, the consented keyring store. A new read anywhere in `src/` fails `a_secret_is_read_only_where_a_login_or_the_identity_provider_takes_it`. The renewal is `azure::renew_silently`, which has no browser path at all, and the provider holds its refresh token (and any rotated one) in memory only — no keyring store, no keyring delete, so the refresh token's homes stay the ones the user's "remember" answer chose. `an_entra_tokens_wire_stores_logs_and_prompts_for_nothing` names every function on the token's wire and pins that none stores, deletes, logs, prompts or formats a token; `tests/db_entra.rs` drives real Postgres logins across an expiry with an injected clock — a script run's, and the grid's renewed by the task alone — and pins the task's end with its pool.

## Capabilities

- Capabilities are declared per *server*, not just per driver: `DbPool::backend_capabilities` consults `PgFlavor` because RisingWave speaks the Postgres protocol but has no read-write transactions. Declaring `transactions: false` is what makes the script tab stop wrapping batches and editing refuse with a reason — hubro's row-count write guard *is* a transaction, so a backend without one is not offered unguarded editing.
- **Prefer narrowing a claim to clearing a capability.** CockroachDB and YugabyteDB hold real transactions that roll DML back and let DDL escape, so they declare `transactions: true` with `transactional_ddl: false` — declaring them non-transactional would be the worse lie, disabling the script tab's atomicity for the case where it does hold. `transactional_ddl` is the one capability that gates nothing: it only decides whether a failed script reports `Rollback::Full` or `Rollback::ExceptSchemaChanges`. When engines disagree on the details of a gap (Cockroach also commits writes staged *before* a DDL; Yugabyte rolls those back), say only what holds on both — claiming less than is known beats claiming more.
- **A UI gate and the path that executes must not answer the same question twice.** `schema_edit_refusal` decides whether to *offer* an operation by generating its statement and handing it to `script_refusal` — the same call the run path makes on the text that finally reaches the server. Per-operation capability rules written beside it would be a second answer, free to drift; and since the statement is editable, only the run path ever sees what actually runs. Deriving one from the other also settles the dialect differences without stating them: SQLite's truncate is a `DELETE`, so it is charged for changing rows rather than for changing the schema, which a hand-written rule would have got wrong.
- **`ddl` is one flag, and two engines have only part of it.** Measured across nine engines (`tests/db_schema_edit.rs`): Materialize refuses `ADD COLUMN`, `RENAME COLUMN` and `TRUNCATE`; RisingWave refuses `RENAME COLUMN` and `TRUNCATE`; the other seven take everything. Deliberately *not* carved into per-operation capabilities — the statement is shown before it runs, and the engine's own refusal is a better message than a flag hubro would have to re-derive for every backend it adds. What the tests enforce instead is the failure *mode*: a refusal the user sees, never a statement accepted while nothing changes.

## Scripts and connections

- **A script never takes a pooled connection per statement.** The atomic path holds hubro's transaction; the sequential path (a script with its own `BEGIN`/`COMMIT`, a statement that can't run in a transaction, a backend without transactions) holds a `ScriptConn` (`registry.rs`); the read-only path holds a `ReadOnlyRun`. Per statement, a script's `BEGIN` opened a transaction on one session while its `INSERT` committed on another — measured on Postgres, CockroachDB and SQLite. SQL Server's hand-rolled pool happened to hand back the same client in a quiet test (it keeps idle clients last-in, first-out), which nothing guaranteed while the grid and introspection share the pool.
- **A run ends outside any transaction, on every path.** A script ending in a read the row cap cut short is not followed by anything — waiting to ask meant draining the rest of the result first (1.3 s on localhost for 3M rows) — so `ScriptConn::finish_with_read` asks before the read. **That is sound only where `final_read_may_close` says the statement can neither touch the transaction nor write**: "returns rows" is the first keyword alone, and measured, CockroachDB's `SHOW COMMIT TIMESTAMP` commits, a SQL Server batch led by `SELECT` can carry `COMMIT` or `BEGIN TRAN`, and a row-returning write (`WITH w AS (INSERT … RETURNING) SELECT …`, T-SQL's `OUTPUT`) is aborted if its connection is dropped before its rows are read (measured: 0 of 3M kept). Anything else is read to the end before the run ends. With nothing open, a cut-short read on a Postgres-wire engine that cannot say whether it wrote has its rest read in a background task before the connection closes (`postgres::drain_then_close`; closing at once aborted `SELECT f()` for a writing function); SQL Server's is discarded, as its capped reads always were. **A cut-short Postgres read is cancelled at the cap when its transaction has written nothing to a table** (the user's decision, recorded on the issue): the statement that sends `pg_cancel_backend` also requires `pg_stat_activity.backend_xid IS NULL`, so a `SELECT f()` that has written is read to its end and keeps its writes; writes rows past the cap would have made are not made. **No xid is not no effect, and the cancel undoes the whole statement, rows before the cap included.** Measured on PostgreSQL 17, atomic and sequential: a `set_config(…, false)` the read made was gone afterwards, and a listener got none of its `pg_notify`s (neither takes an xid; a reviewer's measurement that `pg_notify` does was not reproduced). The same class, unmeasured: `dblink_exec`, `COPY … TO PROGRAM` or `lo_export` run by a function, advisory locks. The decision stands, and the editor's notice says what the cancel undid — on this rule's cancels only (`RestOfRead::CancelledUnwritten`); a marked run's or SQL Server's discarded read gets a plain line (`truncation_notice`); `postgres_capped_read_cancel_undoes_effects_that_take_no_xid` pins it. Only `PgFlavor::Postgres` is asked (`knows_whether_written`): YugabyteDB's `backend_xid` stayed empty while a function inserted rows, and CockroachDB's `pg_stat_activity` has no row for the session, so there the rest is read to its end — never cancel on unknown. The cancel names the session by pid **and backend start time** (a pid alone can be another session on another server behind a load balancer) and requires it to be running the read's text (so a transaction-pooling PgBouncer's other client is left alone) — except one running the identical text on the same backend under the same role, which would be the one cancelled; known and accepted. A `57014` after hubro's cancel counts as that cancel only by its message (PostgreSQL's "due to user request", CockroachDB's untranslated one) or, when `lc_messages` translates it, only if the probe found `statement_timeout` off; a timeout, or an unknown message with a timeout set, is the statement's error (`sqlx_common::cancel_landed`). The cost per read: atomic path one round trip (release the last read's savepoint and open this one's, the first also asking the session; none once the transaction has written; released before a statement hubro runs as a write, so those never run in a subtransaction — a write a read makes, `SELECT f()`, does); sequential path one (`postgres::probe_session`, which also says whether a transaction is open) plus two inside the script's own transaction (savepoint and release); marked connections none (asked once per run; CockroachDB one). Inside a transaction the read runs in a savepoint and a cancel rolls back to it — a cancelled statement otherwise aborts the transaction, and the script's next statements failed with "current transaction is aborted". The last read, outside a transaction, has its rest cancelled or read to its end in the run, so an error past the cap is the read's; only engines that cannot say whether it wrote still read it in the background. A marked connection's run (`ReadOnlyRun`) cancels whatever the statement has done — the engine refuses its writes and its transaction is rolled back regardless — via `pg_cancel_backend` on PostgreSQL and YugabyteDB and `CANCEL QUERIES` on CockroachDB (Materialize ignores a cancel once rows flow; RisingWave cannot take one), or closes the connection when the read is the run's last statement. **The rest of a cut-short read is read by hubro, never by sqlx**: sqlx reads it in the connection's next question, in one poll that never returns `Pending` over localhost — measured, 44 s for 200M rows during which a timer beside the run did not fire and `abort()` did not take effect, on the UI thread the SQL tab's run is polled on. `sqlx_common::collect_capped_then` reads it from the still-open stream and gives the thread a turn every 20 ms — a 1 ms timer, not an immediate self-wake, which Dioxus re-polls before returning to the window's event loop (measured: a Cancel click was not seen until the rest had been read); `postgres_reading_the_rest_of_a_capped_read_leaves_the_thread_to_others` pins it. The one exception is `drain_then_close`'s background read, which runs on a tokio worker, not the UI thread. A refused end-of-run probe counts as a rollback except CockroachDB's commit-wait `25000`, which follows a commit — Materialize sends the same code for uncommitted work. Otherwise `ScriptConn::end` rolls back whatever the script left open and reports it (`ScriptDone::rolled_back`, `Rollback::OpenTransaction`). A connection that goes back to the pool inside a transaction swallows later, unrelated statements: measured, an edit on SQL Server reported success and was lost when the connection closed, a CockroachDB read on another connection waited on the abandoned locks indefinitely, and an aborted Postgres transaction failed every query that landed on it. Whether a transaction is open is asked of the server (Postgres-wire: the `ReadyForQuery` status, through sqlx's `begin_with` check; SQLite: whether a `BEGIN` is refused; SQL Server: `@@TRANCOUNT`), never read off the script's text.
- **A run's connection is closed when the run ends, never returned to the pool** — on all three paths (`ScriptTx` from `begin_script_tx`, `ScriptConn`, `ReadOnlyRun`) and on cancel. Whatever a script leaves on its session goes with it, so there is no per-engine list of things to reset. Measured before, through the pool after a run: on every Postgres-wire engine `SET` (search_path, ROLE, statement_timeout, `default_transaction_read_only`, application_name), temp tables and session advisory locks — the read-only path's per-statement rollback undoes a `SET` but not a lock; on SQL Server `USE`, `SET CONTEXT_INFO`, `EXECUTE AS` and a session app lock (most `SET` options did not leak there: each statement is its own `sp_executesql`); on SQLite PRAGMAs, temp tables, `ATTACH`, and `locking_mode = EXCLUSIVE`, which locked every other connection out of the file. A script's `DISCARD ALL` deallocated sqlx's cached prepared statements, and the next query on that connection failed (PostgreSQL, TimescaleDB, Citus, YugabyteDB, Materialize; CockroachDB refuses the statement). A reset was the alternative and is worse: `RESET ALL` does not restore a role, `DISCARD ALL` is the bug above, and a TDS client cannot call `sp_reset_connection`. The cost is a reconnect per run, and that nothing — a temp table, a setting — carries from one run to the next. The sqlx connections are marked `close_on_drop` when checked out (`sqlx_common::acquire_for_run`), which is what covers a cancelled run and `ScriptTx`, whose sqlx `Transaction` owns its connection; SQL Server's script holds discard theirs in `Drop`. `tests/db_script_session.rs` pins it per engine for the atomic and sequential paths (a lone statement, the script's own transaction ending in a read, and on most engines a read the row cap cuts short), on pools of one connection so the probe cannot miss the script's. The read-only path is pinned there only through a session advisory lock, on PostgreSQL, TimescaleDB and Citus; SQLite's read-only run is safe by construction, on a connection of its own that never was the pool's. Cancellation is pinned in `tests/db_script.rs` (`*_cancelled_script_does_not_return_its_transaction_to_the_pool`). The import is the deliberate exception: it runs only `INSERT`s hubro builds, so its transaction (`DbPool::begin_pooled_tx`) returns its connection, which `sqlite_import_returns_its_connection_to_the_pool` pins.
- **Rolling back is the conservative default, not a settled design.** A transaction that spans runs (`BEGIN` in one, `COMMIT` in a later one) would need a connection pinned to the editor tab, with the grid and edits still on the pool beside it; that is the user's call. Meanwhile the consequence is real: `BEGIN`, `UPDATE`, `ROLLBACK` run as three selections autocommit the `UPDATE`, and on Postgres-wire engines the lone `ROLLBACK` succeeds with a warning while undoing nothing — the left-open note on the `BEGIN` run is what tells the user. Don't "fix" a rollback report by committing.
- **SQL Server transaction control runs as a plain batch** (`tsql_is_transaction_control`). Through `sp_executesql`, `BEGIN TRAN` fails with error 266 and has still opened its transaction. Keep the match strict — stricter than the gate's, whose name slot takes any word (`BEGIN TRAN EXEC('SET NOCOUNT ON')` passes it): a plain batch is where a `SET` outlives its statement, which the `NOCOUNT OFF` pin depends on not happening.
- **A SQL Server statement that creates a `#temp` table runs as a plain batch, on a run's own connection only, and is checked after** (`tsql_route`, `tsql_creates_temp_table`, `checked_batch`). `sp_executesql` is a scope, and a local temp table is dropped with the scope that made it, so the next statement could not see it; created at session scope, every later `sp_executesql` sees it. **The safety claim rests on the post-check, not on any word list**: a plain batch has no error 266, which `sp_executesql` raises whenever `@@TRANCOUNT` changed across the call, for *any* cause. Measured in review, a creator inside `BEGIN TRY … END CATCH` whose DDL a database trigger rolled back (3609) returned normally with hubro's transaction gone, and the next `INSERT` persisted in autocommit. A deadlock victim (1205) is not that shape — measured, it dooms the transaction and the server ends the batch with 3998 on either route; a trigger's rollback leaves nothing doomed. The transaction id also catches a trigger that rolls back and reopens, keeping the count, which 266 itself missed. So `@@TRANCOUNT` and the open transaction's id are read before and after the batch, and any change fails the statement as 266 would (atomic path: `AlreadyEnded` at that statement). When a route trades a server-enforced check for a lexical one, add a post-condition on the state rather than extending the list. The words in `tsql_creates_temp_table` are a first filter for what else a plain batch changes: a `SET` outlives the statement (measured, a plain batch's `SET NOEXEC ON` makes hubro's own `COMMIT` a no-op), and tiberius's `simple_query` reports no affected-row counts at all, so a write, an opaque word or an `INTO` anywhere but a read's own temp table stays on `sp_executesql` — which is also why not every statement goes as a plain batch, though the issue proposed it. Never on a pooled connection: the table would reach the next borrower.

## Read-only enforcement

- **A connection the user marked read-only is refused twice: by the gate, and by the engine.** `script_refusal` reads each statement and explains the refusal up front; it cannot be airtight (a hand-written lexer, and writes no keyword shows: `SELECT setval(…)`). So `run_script` runs a marked connection's scripts through `ReadOnlyRun` (`registry.rs`) whenever `engine_has_read_only_mode`: SQLite on a separate connection opened `SQLITE_OPEN_READONLY`, Postgres-wire engines with **each statement in its own `BEGIN READ ONLY` transaction, always rolled back**. The decision is made per run from the effective capabilities, so a change of marking applies on the next run with nothing to re-apply — don't move it into pool setup.
- **Don't replace either mechanism with a session setting** — all three the issue first proposed were measured to be undone by statements the gate passes. `PRAGMA query_only = 1` falls to `PRAGMA query_only = 0; DELETE …` in one string (sqlx-sqlite runs every statement in a string). `default_transaction_read_only = on` falls to `SELECT set_config('default_transaction_read_only', 'off', false)` and to `BEGIN READ WRITE`, both of which the gate reads as a read and as transaction control. A script-long read-only transaction ends at the script's own `COMMIT`. Per statement works because sqlx's extended protocol carries exactly one command, so a statement can end or reopen hubro's transaction only as the whole of itself, and the next statement gets a new one.
- **The engines differ, and the tests are where it shows** (`read_only_backstop` in `script.rs`, `tests/db_read_only.rs`). CockroachDB's `autocommit_before_ddl` commits the read-only transaction ahead of a schema change, which then succeeds — hence `SET LOCAL autocommit_before_ddl = off` in its `BEGIN` (`postgres::read_only_begin`; `SET LOCAL` keeps it off the pool, where turning it off breaks `ALTER` on schema-locked tables). Materialize's read-only transaction *accepts* `CREATE TABLE` and makes it permanent on `COMMIT`, so there the always-rollback is what keeps it out. YugabyteDB commits DDL as it runs but refuses it inside a read-only transaction. RisingWave's `BEGIN READ ONLY` is the one real transaction it has.
- **SQL Server has no read-only mode, so the gate is all there is.** `ApplicationIntent=ReadOnly` is routing, not refusal (measured: a table was created and written through it). `tests/db_read_only.rs` pins that `SELECT NEXT VALUE FOR s` advances a sequence on a marked SQL Server connection; the connection form's hint says so too, keyed on the same `engine_has_read_only_mode`. Don't fake it with an always-rollback transaction — T-SQL's own `COMMIT` ends it, and sequences and identity values escape rollback anyway.
- **The boundary is this backend's transaction, so name new escapes as members of that class.** The engine refuses a write *inside* the read-only transaction; anything that leaves it — another connection, the WAL, the filesystem, another process — is out of reach, and a "found another one" is a list entry in `WriteProtection::ReadOnly`'s docs, not a mechanism change. Known members: SQL Server (no such transaction at all); `dblink_exec`; Citus's `run_command_on_*`, which writes to this very database through its own connection (pinned in `tests/db_read_only.rs`, like SQL Server); `pg_terminate_backend`; session-level advisory locks; `pg_logical_emit_message`; `lo_export`; `pg_create_physical_replication_slot`; SQLite's `VACUUM INTO`. Don't answer one with a function-name blacklist in the gate — that is the keyword scan this backstop exists because of. `pg_notify` is *not* a member: the engine allows it, but it is delivered on commit and the always-rollback discards it — which is one more reason the rollback must never become a commit. Nor is a `postgres_fdw` foreign table: writing to one is an `INSERT` here, refused in this transaction (measured on a loopback server).
- **On Materialize a marked run can report a schema change as done while nothing changes.** Its read-only transaction accepts the DDL and hubro's rollback discards it, so the statement "succeeds" with 0 rows affected. That breaks the schema-editing rule above (a refusal the user sees, never a statement accepted while nothing changes) — knowingly: it is reachable only past the gate, through a lexer mismatch hiding DDL, and the alternative is the DDL persisting.

## Object metadata

- Objects that are the database's own bookkeeping (extension schemas and tables, child partitions) are declared per backend as `TableMeta::internal` during introspection — never inferred from name patterns. The sidebar hides them behind one toggle and the SQL editor demotes them in completion ranking, so every new backend inherits both by filling in that one field. `TableMeta::kind_label` is the matching hook for engine-specific vocabulary (`hypertable`, `continuous aggregate`), rendered as a badge that refines `TableKind` rather than replacing it.
- A SQL Server table with an enabled INSTEAD OF trigger is declared `INSTEAD_OF_TRIGGER` (read from `sys.triggers` in introspection). The count the server reports for a statement the trigger replaced is the rows it *fired for*, whatever it wrote — measured: four rows imported, two landed, 4 of 4 reported — so no row-count guard can check a write to it, and editing and import are refused rather than unguarded. One trigger kind restricts the whole table: editing is one capability. Disabled triggers don't fire and views keep their own reason. Postgres-wire engines have the same hole through a different door: INSTEAD OF triggers exist only on views there, and a BEFORE trigger returning NULL lowers the count the guard reads (measured, 17.10), but a `DO INSTEAD` rule on a table replaces the statement and its command tag — an `UPDATE` redirected elsewhere reports `UPDATE 1` with the table untouched (measured on PostgreSQL, TimescaleDB, Citus and YugabyteDB). Such a table is declared `INSTEAD_RULE`, from `pg_rewrite.is_instead` on anything but a view, whose `_RETURN` rule is one too. `DO ALSO` rules keep the statement's own tag and restrict nothing. CockroachDB, Materialize and RisingWave cannot create rules and report an empty `pg_rewrite`, so the query runs everywhere and a failure of it fails introspection rather than leaving such a table editable.
- An object with **no rows hubro can show** is declared `Restriction::NoRows`: a RisingWave sink, which writes outward and stores nothing, or a SQLite object the engine can list but not resolve (a virtual table whose module hubro's SQLite lacks, a view calling a missing function or reading a dropped table), which SQLite introspection lists with no columns rather than failing the whole tree. It is the one restriction that narrows *reading* as well as writing. `TableAccess::resolve` derives the read gate from the object's own declaration and never from the write chain, which short-circuits on a read-only connection; `resolve_protected` has to carry it over explicitly, since rebuilding `caps` from the marking would hand the read capability back. Every other restriction (view, materialized view, key-less table) leaves browsing alone — they lack a way to address one row for writing, not rows to show.
