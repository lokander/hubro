# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

More specific guidance lives next to the code it governs, and loads when you work there:

- `src/db/CLAUDE.md` — engine flavors, introspection SQL, retrying, capabilities, object metadata.
- `src/ui/CLAUDE.md` — the Dioxus 0.7 API rules. **Read this before writing any component**; 0.7 changed every API and pre-0.7 patterns from training data will not compile.
- `tests/CLAUDE.md` — which engine needs which env var, the container layout, verifying a new engine, the support matrix.
- `docs/interactive-testing.md` — how to drive the app on Linux, macOS and Windows.

## Project

`hubro` is a **desktop-only database viewer** (SQLite and Postgres via sqlx, SQL Server via tiberius) built with Dioxus 0.7 (Rust), shipping on Linux, macOS, and Windows. Do not add web or mobile platform support. Work is tracked in the Linear project "hubro" (team FRE).

Licensed **GPL-3.0-only**, with copyright held solely by Fredrik Lokander — which is what keeps commercial dual-licensing possible. Two consequences: don't add dependencies under licenses GPL-3.0 can't incorporate (AGPL, or proprietary/source-available terms; permissive and MPL are fine), and don't merge outside contributions without a CLA or copyright assignment, since divided copyright permanently removes the ability to relicense.

## Commands

- `dx serve` — run the desktop app with hot reload.
- `dx build` — build the app via the Dioxus CLI.
- `cargo check` / `cargo clippy` — type-check and lint without the Dioxus CLI.
- `cargo fmt --check` — CI enforces rustfmt (the Actions job runs fmt, clippy, and test); run it before every push.
- **A PR's CI runs all three OS legs** (Linux, macOS, Windows), the same matrix as a push to `main`. The repo is public, so GitHub's standard runners cost no Actions minutes on any OS. PRs used to check Linux only, to save minutes the repo was never charged, so platform breakage surfaced on `main` after the merge: one batch of three Windows failures across two merged PRs had no `cfg` block at all (a path, a `file://` URL, two byte-exact comparisons). Wait for every leg in `gh pr checks`. macOS and Windows finish well after Linux, so the first green check is not the last. When one of them goes red, the usual causes are `cfg` blocks, path *syntax* (separators, drive letters, UNC, `file://`), a test comparing a checked-in file byte for byte or matching one against a literal `\n`, and process, signal or keyring code. `gh workflow run ci.yml --ref <branch>` is now only for a branch with no PR. The Linux leg also runs the Postgres suites twice, against 17 and then 18 (`tests/CLAUDE.md` says why).
- Tailwind is compiled automatically by `dx serve` (Dioxus 0.7+): it picks up `tailwind.css` next to Cargo.toml and outputs to `assets/tailwind.css`. No npm/Tailwind CLI setup is needed.
- `assets/tailwind.css` is generated but tracked, so every UI branch touches it: resolve a conflict by re-running `dx build`, never by hand — a plain `--theirs` silently dropped 41 lines of a sibling PR's classes. The scanner reads Rust **doc comments** too, so naming a CSS property in prose emits a dead utility into the file.

- `cargo test` — run all tests: unit tests live in `#[cfg(test)]` modules next to the code, integration tests in `tests/`. Test fixture files go in `tests/fixtures/`. Run a single test with `cargo test <name>`. **The split is forced, not stylistic**: `tests/` compiles as a separate crate and can only reach `src/lib.rs`'s nine `pub mod`s, while `src/` holds 219 `pub(super)` items and 1,234 private fns. Every policy this project extracts "as a free function over plain data, where a test can execute it" is `pub(super)` — reachable from a colocated test, invisible to `tests/`. Moving those tests to `tests/` would mean publishing the private API in order to test it, so don't; 70% of the suite (704 of ~1,006) is colocated for this reason.
- Don't run `cargo test` and `dx build`/`cargo build` concurrently — they contend on the `target/` lock (spurious signal/exit 144); run them sequentially.
- Don't pipe `cargo test` into `head`/`grep`: SIGPIPE can kill the run mid-fixture and leave an engine database half-set-up, so the *next* run fails on leftover state rather than on code. Redirect to a file and grep that.
- **A green engine-test run can mean nothing ran**: every `tests/db_*.rs` skips *and passes* when its `HUBRO_*_TEST_URL` is unset, so a stopped container or a typo reads as success. Confirm the tests executed, and mutation-check load-bearing assertions (invert one — it must fail). That caught an assertion in an unreached branch, a boundary defended only by a doc comment, and a guard with an escape route. Mutate the **decision**, not just its placement: a source-reading test pins where a call sits and stays green when its polarity flips, which let a mutation store a secret the user had declined — so extract a consequential policy as a free function over plain data, where a test can execute it. Run one control mutation you expect to *pass*, too; one that failed exposed an assertion that required dead code. When the control does pass, read it as a question rather than a reassurance — it says nothing pins the claim that code was making. The schema-editing work's control (dropping SQL Server's explicit `NULL`) passed the nine-engine sweep exactly as predicted, which is how a doc comment justifying the keyword by `ANSI_NULL_DFLT_OFF` came to be measured and found false. A comment that justifies code by *engine* behaviour is answerable in minutes against a running container; ask it rather than reasoning about it. Which variable each engine needs, and how to start them, is in `tests/CLAUDE.md`.
- **Mutate the guard, not just the code it guards.** In the review of a fix to how the "remember this passphrase" answer is parked between prompts, every finding after the second round was in a *test* rather than in the fix, and each one passed a full suite: `contains("remember,")` matched `remember: !remember,`; `contains("source")` was satisfied by the word "session-sourced" in a **comment**; a test parked state into a map the function under test could not reach, so it could not fail whatever the code did; a no-clobber rule was pinned for one of three keys. Read every source-reading assertion as "what mutation does this still allow?" — strip comment lines before matching, pin a field or binding **as written** (whitespace-collapsed, so a rustfmt wrap is a reformat rather than an alarming failure), and prefer `lines()` over a literal containing `\n` (that is the Windows line-endings trap behind the CI failures above, and `tests/line_endings.rs` is the registry of files that depend on the answer).
- **Defend the wire, not the spot where the bug was.** Each of those fixes pinned exactly where the last instance had been found — one field, then one arm, then one function — and the next instance sat one hop outside it: the call site once the binding was pinned, the caller's gate once the call was pinned. It stopped only when a single test named the whole path a decision travels (`the_remember_answer_is_not_inverted_at_any_hop_of_its_wire`: card → submit → park → withdraw/redeem → prompt → card, plus the gates deciding whether any of it runs). When a value routes a consequential decision, ask where it is *consumed* — every keyring write or delete gated on it — and cover every hop to there. A per-function sweep invites the next round.
- **Mutation checks have a budget.** Each one edits `src/`, so cargo recompiles the crate and relinks every test binary that depends on it (~100 MB each with split debuginfo, ~400 MB without; the source-reading tests use `include_str!`, so they rebuild too). Fifteen mutations are fifteen full builds, and one batch of three agents' matrices kept the build disk saturated for hours. So: an ordinary bug fix gets one check — revert the fix, a test must fail. A consent/security, data-integrity or engine-policy decision gets one mutation per consequential decision (its polarity, the gate that decides whether it runs) plus one control, about five per PR at most — pick the hops a wire test names rather than enumerating every line. A surviving mutation gets at most one new test, or a one-line reason it is equivalent, then stop. Purely visual UI code gets none. Reviewers reuse the author's results and mutate only what they doubt.
- **Two agents cannot share one container set.** Every suite uses fixed fixture names against one database, so concurrent runs drop each other's tables — measured, not theoretical: two `db_cockroach` runs against the same set fail 3-6 tests each, and against separate sets both pass. So parallel work on several issues needs `./scripts/test-db.sh up <N>` per agent (ports are `base + N*100`, container names get a `-N` suffix, set 0 is the layout the headers document), then `./scripts/test-db.sh test <N> [engines] -- <cargo test args>`, and `rm <N>` to release it. Not `env $(./scripts/test-db.sh env <N>) cargo test`: when `env` refuses, that still runs cargo with no engine variables, and every engine suite skips green (`tests/CLAUDE.md`). Worktrees isolate the code but **not** the build: a fresh one has no `.cargo/config.toml` (untracked, via `.git/info/exclude`), so it builds cold into its own `./target`, on whatever drive the worktree sits on. Write one per worktree pointing at a target dir of its own on the machine's build drive (where that is, and where worktrees go, is machine-specific: the machine's global CLAUDE.md says), and `cp -a --reflink=always` a warm target dir into it, which costs nothing on btrfs, so the first build starts warm. Put `split-debuginfo = "unpacked"` under `[profile.dev]` in the same file: with DWARF inline, every test binary was ~400 MB and a full `cargo test --no-run` wrote ~100 GB per slot; split, they are 86-121 MB, the target dir is 9.7 GB, and a clean build took 1m25s. Every slot needs the setting, or the copied cache doesn't match and rebuilds cold. Never start several cold builds at once (after a toolchain update, or with a fresh target dir): three in parallel ran 90+ minutes on a saturated disk. Build one slot, then copy it to the others. Process names are shared too: every worktree builds a binary called `hubro`, so `pkill -x hubro` (or `pkill -x Xephyr`) kills the siblings' — kill by recorded PID.

The crate is split into a library (`src/lib.rs`, holds app modules) and a thin binary (`src/main.rs`) so integration tests can import app code as `hubro::...`.

When a live database server (e.g. Postgres) is needed for testing or development, run it in Docker — never install or run database servers directly on the host.

Git pushes use SSH; the key is passphrase-protected. If pushes fail with "Permission denied (publickey)", ask the user to run `ssh-add`, or temporarily switch the remote to HTTPS with the authenticated `gh` CLI (`gh auth setup-git`).

## Interactive testing

Nothing in the suite covers rendering, so a UI change wants the app driven: one change's model tests all passed while the screen stated the reason twice and still offered Export on an unbrowsable object. Three sessions running, driving the app has caught bugs a green suite passed. The per-platform recipes, and the rule about isolating the app's config while doing it, are in **`docs/interactive-testing.md`**.

## Issue workflow

Work is tracked in Linear (team FRE). **Never write a Linear issue ID into a tracked file** — code, comments, test names, docs, this file. The repository is public and the Linear project is not, so an ID is a dead link to every outside reader, and finished issues are deleted (see Milestones). State the reason itself; `tests/no_issue_ids.rs` fails on any ID in a tracked file. The same goes for PR descriptions and PR comments, which are just as public: no "Closes" line naming the issue. Linear links the PR through the branch name. Older PRs that carry IDs stay as they are.

Docs-only changes (CLAUDE.md, README, etc.) may be committed directly to `main`; all other work follows this flow:

1. Move the Linear issue to In Progress. Create a **git worktree** on the issue's branch (use Linear's suggested branch name, e.g. `lokander/fre-<number>-short-issue-title`), and do all work there. **Reproduce before building the fix the issue proposes** — treat its diagnosis as a lead and its fix direction as a hypothesis. All three bugs in the 2026-08-11 batch were wrong about themselves: one issue's line numbers had drifted onto struct definitions, another's stated cause (cargo running test binaries in parallel) is false — cargo runs test *targets* sequentially — and the third's suggested fix was built, driven against a real bastion, and observed to still fail.
2. Commit (conventional, subject-only), push the branch, and open a **GitHub PR** with `gh pr create`. Linear links the PR to the issue through the branch name.
3. Spawn a **subagent to review the PR** (correctness, the Dioxus 0.7 rules in `src/ui/CLAUDE.md`, scope vs the issue). `gh pr review --approve` is blocked as self-approval — post findings with `gh pr comment`. Fix blocking findings and re-review by resuming the *same* review subagent via SendMessage (keeps its context). Only proceed once it approves. Expect findings to be *claims* rather than broken features — a doc comment, README cell or `# validates` comment asserting a property nothing checks. Prefer making such a claim checkable over restating it (`tests/support_matrix.rs` is the pattern); a guard that cannot fire is worse than none, because it reads as handled. Mutate the **fix** too, not just the code it fixes: a correct fix that no test pins is one commit from regressing, and one such fix survived reverting to the exact pre-fix code with 485 tests still green.

   A second reviewer **on a different model, handed the diff cold**, is worth it on anything consent- or security-shaped. On the remember-passphrase fix, the first reviewer had approved a seam and declared the defect class closed when a fresh one inverted a binding a single line above the pinned field and left 713 tests green. It also re-derived the change's load-bearing reachability argument independently, which is the corroboration that actually mattered — one reviewer converges on the class it has been finding and stops seeing the class it has not. Expect the valuable output to be *why* the fixes keep missing rather than one more instance; that is what turned eight rounds of whack-a-mole into a single test.

   Treat "the issue is wrong about itself" as the default rather than the exception. That same issue's first bullet asked for a migration that turned out to *be* the bug, and reversing it took both reviewers tracing the same call graph separately. Correct the issue description before moving it to Done, marking what was wrong rather than deleting it — the wrong diagnosis is the part worth keeping — and say it in the PR description too, which outlives the issue.
4. **Wait for CI to pass** (`gh pr checks <n> --watch`) before merging — local clippy/test runs don't cover everything CI checks (e.g. rustfmt). With several PRs in flight, rebase each onto `main` locally and build before merging: GitHub's `MERGEABLE` is textual, and a conflict-free merge still failed to compile when a sibling added a field to `SavedConnection`. Then **remove the worktree first**, and rebase-merge (`gh pr merge --rebase --delete-branch`) from the main checkout — merging from inside the worktree fails trying to check out `main`. Run the merge as its own step (chaining a `gh pr comment` + merge in one command trips the self-merge classifier). Move the issue to Done with the PR linked.

**Running several issues at once.** At most three worker agents at a time: a batch of five hit the session limit twice, and almost all of the tokens went on subagents' building, measuring, mutating and reviewing, not on orchestration. Spend less without lowering quality:
- Batch each agent's mutation checks into one script. Commit first: the script restores with `git checkout`, which wipes uncommitted edits.
- Run targeted tests while iterating, and the full suite once before pushing.
- Reviewers reuse the author's measurements and re-review through `git range-diff`.
- Keep the cold second reviewer (step 3) for consent, security and data-integrity changes (transactions, writes) and nowhere else. On a transaction fix it caught regressions the first reviewer had missed.
- Don't move re-reviews to a cheaper model: a fix can bring in a new bug that a weaker check misses.

A same-area finding (the same bug class one hop away, a stale comment, a small adjacent fix) gets fixed in the PR it was found in, not filed as a follow-up.

### Milestones

Milestones are **scoped deliverables that complete**, not categories. Three rules:

- **Never add an issue to a finished milestone.** Finished milestones get deleted with their issues (below), so the added issue would be deleted with them. Linear also computes progress from the issues, so it would drop a 100% milestone below 100% until then, and has no way to un-complete a milestone.
- **Don't create catch-all milestones.** A milestone with no completion condition ("Misc polish", "Follow-ups") sits at partial progress forever. Loose work gets **no milestone** plus a `Feature`/`Bug`/`Improvement` label and lives in the project backlog. `Nice to have (future)` is the one deliberate exception — designed-but-deferred work, not a general backlog.
- **Finished milestones and their issues get deleted** to stay under Linear's issue limit, which has blocked issue creation before. So nothing may depend on an issue surviving: the reasoning lives in the code, its comments, commit subjects and PR descriptions.

## Releases

A release is cut by pushing a `vX.Y.Z` tag; `release.yml` bundles five artifacts (deb, AppImage, dmg, msi, setup exe) and publishes them with generated notes.

- **The version is authored in two files, and only one is obvious.** `Cargo.toml` is what dx stamps into the Linux and Windows artifacts; `packaging/macos/Info.plist` (`CFBundleShortVersionString` **and** `CFBundleVersion`) is what the macOS bundle carries, because dx *replaces* its generated plist with that file rather than merging. Measured against the v0.8.0 artifacts: the deb's control says `Version: 0.8.0`, the packaged exe's VERSIONINFO says `ProductVersion 0.8.0`, and the shipped `Hubro.app/Contents/Info.plist` is byte-identical to the checked-in one. Nothing else authors a version — `tests/file_associations.rs` now pins that absence across `packaging/` and `Dioxus.toml`.
- **Order, because getting it wrong is invisible afterwards:** bump both files, commit `chore: release vX.Y.Z`, push, **wait for all three CI legs**, then tag *that* commit. `v0.6.0`'s tag names a commit whose `Cargo.toml` still said `0.5.0`. The dmg's *filename* comes from `Cargo.toml`, so a stale plist ships as `Hubro_X.Y.Z_aarch64.dmg` containing an app that tells Finder and Gatekeeper it is the previous version — invisible from the release page.
- **Two guards, deliberately on different triggers.** `tests/file_associations.rs` pins the plist to `Cargo.toml`, so a `Cargo.toml`-only bump reddens **all three** CI legs (not a flaky macOS leg — the test reads the checked-in file everywhere). `release.yml`'s `verify` job re-checks both against the tag before any bundle job runs, because the test only runs on a push to `main` and a tag cut from a stale checkout never meets it. The gate was proved end to end with a throwaway tag: `verify` failed, all three bundles and publish skipped, no release created.
- **A tag pushed while Actions is disabled produces no run**, and deleting and re-pushing it does not reliably create one (observed on v0.7.0). Build it by hand: `gh workflow run release.yml --ref main -f tag=vX.Y.Z`.
- Artifacts are **unsigned**, so Gatekeeper and SmartScreen both warn on first launch; the README documents the workarounds. Green release jobs prove the bundles *build*, not that they run.

## Commits

Use [Conventional Commits](https://www.conventionalcommits.org/) with **subject line only** — no body, no footers (including no Co-Authored-By trailers). Example: `feat: add csv import`.

## Architecture

- `src/main.rs` is a thin binary: it parses CLI arguments and calls `dioxus::launch`. Components live under `src/ui/`, the backends under `src/db/`, and config under `src/config/`; each of those has its own guidance file where one is warranted.
- The rest of the top level, none of which has a guidance file of its own: `src/cli.rs` (argument parsing and the file-association open target), `src/history.rs` (query history), `src/secrets.rs` (the keyring, with a session-only fallback behind `HUBRO_DISABLE_KEYRING=1`), `src/tunnel.rs` (SSH tunnels), `src/azure.rs` (Entra sign-in), `src/util.rs`.
- Static files live in `assets/` and are referenced via the `asset!("/assets/...")` macro (paths are relative to the project root). Stylesheets/favicons are injected with `document::Link` in `App`.
- `Dioxus.toml` holds Dioxus CLI app configuration: the bundle identifier, icons (order is load-bearing — read the comment), and the per-platform file associations. `packaging/README.md` explains why each platform's declaration looks different.
- New fields on `SavedConnection`/`Settings` use `#[serde(default, skip_serializing_if = ...)]` so older config files still deserialize and unaffected entries serialize unchanged.
- The app was renamed from `dataview` before it had any users, so there is deliberately no migration code. The name is load-bearing in `$XDG_CONFIG_HOME/hubro/` (connections, settings, session, SSH known_hosts), `$XDG_DATA_HOME/hubro/history.db`, the `hubro` keyring service, and the `no.lokander.hubro` bundle id — changing it again would strand all four.
